# 同岗位大样本研究 SOP

目标是抽象岗位能力与责任结构，再映射个人。默认全国同岗位研究，城市主要用于后续岗位机会、薪资与迁移成本筛选。用户明确要求地方市场专项时才限制地区。不同城市的任务可能共通，但企业类型、业务领域、产品阶段和责任层级必须分层验证，不能先假定完全一样。

## 1. 固定研究对象与时间

先写研究卡：业务对象、岗位责任、经验层、纳入/排除、采集日。示例为“中高级B端/企业Agent应用产品经理，全国”；武汉是个人求职偏好，不是能力语料的默认边界。不从个人简历强项决定研究维度。

记录采集时间和页面标明的发布/更新时间。默认优先最近90天有日期的岗位；仍可见但发布日期不明的单独分组，不能把采集日当发布日期。语料刷新原则：新诊断先复核关键来源；最新一轮采集应在30天内。不用历史校招、无日期转载或缓存摘要证明“最新变化”。

## 2. 检索矩阵：多轮、多入口、按缺口调整

检索矩阵必须随职业重建：岗位别名 → 工作对象与结果 → 决策/责任词 → 层级与分工 → 招聘渠道。例如数据分析查业务分析/经营分析/数据分析及指标定义、实验、决策支持；客户成功查客户成功/客户经营及采用、续约、风险、扩展。以下企业AI词表与查询是已有模块的示例，不能成为所有职业的固定查询。

| 检索轴 | 起始词/方向 |
|---|---|
| 岗位别名 | AI产品经理、大模型应用产品经理、Agent产品经理、智能体产品经理、AI应用产品负责人 |
| 业务任务 | 企业办公、政企、SaaS、知识管理、客服、销售、供应链、流程自动化 |
| 责任词 | 需求建模、方案取舍、验收、评测、Bad Case、数据闭环、灰度、成本、人工介入 |
| 层级 | 资深、高级、专家、负责人、5年以上；标签和职责正文分别看 |
| 渠道 | 企业官方招聘；BOSS/猎聘/智联/前程无忧/拉勾等独立平台；企业发布的公开招聘公告 |

执行顺序：全国宽检索→按平台分别检索→按企业官网补正文→按业务/责任/层级补空白→查反例→留出检验。起始不加城市，补查时才按城市检验差异。不能用同一网站多次查询代替多来源。

查询例（替换词组合，避免只使用一个长查询）：
```
"Agent产品经理" "企业" "评测"
"大模型应用" "产品经理" "5年"
site:careers.tencent.com "产品经理" "Agent"
site:job.meituan.com "产品经理" "企业"
site:liepin.com "AI产品经理" "办公"
site:zhipin.com "智能体" "产品经理" "SaaS"
site:zhaopin.com "AI" "产品经理" "验收"
```

一轮不是固定几条搜索，而是覆盖一项明确缺口的检索与正文复核。记录查询、渠道、返回线索、打开/失败、有效增量、仍缺的行业或责任。搜索结果列表只做发现；官网也是发现渠道之一，JS页面或正文不可读时不能仅凭“官网”标完整。

## 3. 采集规模与独立性

**初始采集目标：150–200条候选，80–120条去重后的同岗位完整正文。** 深度岗位画像的首轮发布门槛：至少60条完整、去重、同职责JD，25家独立雇主，4个有效采集渠道，包含官方招聘与至少两个独立招聘平台；最大单一渠道占比不超过50%。优先达到80–120条，而非刚达60就停止。

这是为纠正小样本与渠道集中而设的产品研究门槛，不是科学代表性的保证，也不是任何职业通用的理论样本量。保留大量、多渠道、正文核验和反例研究原则；对其他职业按实际供给说明覆盖，不能将这组工程门槛变成每次个人诊断的手续。稀缺岗位未达门槛时继续换路径；最终受访问/公开供给限制时可以交付明确的阶段性建议，但不能冠以“大样本深度市场画像”，也不能用排除岗位或摘要凑数。

候选量、完整正文量、最终纳入量、雇主数、渠道数分开统计。企业官网汇总为一种渠道，不因25家官网算成25个渠道；多个镜像域名只算同一平台。匿名猎头客户不能假装是多个已知雇主，其占比另记。转载回原岗位，多个城市同一职责模板合并为一个独立岗位模板，地点仍保留为属性。

默认覆盖至少三类企业/业务群（如企业服务、行业内部应用、政企），每个核心群争取10条独立正文；职责层级不只看互联网大厂或初级AI运营。用户若指定单一行业，则在该行业内覆盖企业规模与产品阶段，不为凑多样性混入无关职业。

## 4. 来源登记与正文核验

来源记录包括URL、企业/招聘主体、角色、业务对象、地区、经验、发布日期、采集日期、职责短摘述、正文可见性、纳入理由和去重组。只读可访问页面；优先目的明确的工具/API和正常网页读取。遇到限制换渠道、企业源或公开公告，不绕过访问控制，不让用户承担采集任务。

来源层：target_market=全国目标同岗位职责（role_first）；role_benchmark=相邻子岗位共享任务的补充参照；work_practice=官方方法。主语料数量只计目标同岗位，benchmark与实践分开。官网/平台是渠道，目标/参照/实践是用途，两者不能混为一谈。

当正文不可读，保留线索和失败，不用搜索摘要填正文。可重新查询企业名+职位名找原始公告；找到另一平台同一岗位后仍算一条。有限的已提供JD仅能支持对应范围，不满足批量画像门槛。

## 5. 从语料归纳，禁止拿固定六维反向填材料

1. 将每条JD拆为“业务问题—工作任务—决策责任—产物—质量/结果条件”。记录硬要求、职责、优先项，关键词出现不等于独立能力要求。
2. 开放编码：先从语料产生候选能力、任务和新机制，再合并同义项。六维框架只是展示候选，不是研究答案。保留不能被旧六维解释的新任务。
3. 建立JD×任务矩阵和企业×任务矩阵。样本出现率用独立雇主或岗位模板为分母，报告分子与分母；同企业大量发布不能主导结果。仅称“采集样本中的分布”，不外推全市场比例。
4. 分企业类型、业务域、产品阶段和责任层检查：哪些是跨组共通要求，哪些是特定子岗位要求，哪些只见于少数企业。平台/评测/增长岗位可解释相邻需求，不计入应用岗共通频次。
5. 输出能力之间的关系：基础、前置、瓶颈、结果责任。说明“为何业务要求这个能力、它解决什么失败、对中高级责任意味着什么”。频次不是重要度，硬门槛、任务失败损失和责任深度也参与判断。
6. 查反例：没有上线硬要求的应用岗、以方案为主的行业岗、已有小规模闭环的成功案例等。避免所有候选人都被导向“先做一个Agent”。与既有结论冲突的材料须进入分析。
7. 再用官方技术/产品实践解释机制。招聘数据描述职责；实践解释怎么完成；二者不能互相冒充。当前横截面不能直接证明“今年正在变得更重要”，趋势需时间窗口对照。

## 6. 留出、补查与停止

建模前保留约20%的同岗位正文作留出集，按渠道与雇主分层，避免同企业近重复泄漏。检查框架能否解释新任务和责任，而非只检查是否能塞入已有标签。发现新核心任务就重新编码和补查。

停止必须同时满足：数量/来源门槛、核心业务与责任层覆盖、最近两轮不同策略的增量批次（每批尽量10条有效正文）没有新增会改变核心能力关系或个人投资排序的任务、反例与留出复核完成。个人第一行动稳定，只能作为访谈停止条件，不能成为研究充分的证明。

不得因数量门槛达到就自动声称代表性；若仍有明显渠道/行业偏差要继续补查或缩小结论范围。语料不足时，限制放在研究说明，正文仍给能支持的具体判断。

## 7. 研究交接包

保存来源登记、查询/失败日志、去重关系、纳入排除、任务编码、分组分布、能力关系、新发现/反例、留出结果和停止理由。完整岗位语料层可以由宿主另存JSON/CSV；现有market_model只是报告层摘要，不足以保存整套语料分析。

先形成独立岗位研究备忘录，再映射个人并成稿，最后转诊断JSON供渲染。禁止先填完报告字段，再补几条链接当市场研究。本SOP规定工作过程，不声称本地脚本已经实现自动搜集或语料分析。

使用[研究到成稿契约](synthesis-and-delivery.md)保存来源并运行`audit_corpus.py`。检查器只计算登记与门槛；正文完整性、同岗位判断、任务编码仍须Agent审查。检查未通过时将研究缺口写入交接包，主报告给出范围内的明确建议；不得把打开/尝试的页面数说成有效招聘数，更不能用个人建议已经稳定代替市场画像验收。
